1. [V15-STAGE-BLOCK-001] Final destructive classes bypass complete identity
   and live-handle uniqueness proof.

   Location:
   - extension/su_ai_plugin/core/duplicate_repair_proposer.rb:552-691
   - extension/su_ai_plugin/core/duplicate_repair_proposer.rb:717-906
   - extension/su_ai_plugin/core/duplicate_repair_proposer.rb:913-1006

   Problem:
   verify_class_identity checks only each two-member issue class before
   deduplicate_classes merges those classes. The final merged class is not
   rechecked. A and C can therefore alias the same live handle while A-B and
   B-C each pass their local check. The reproduced exact-three-member case
   emitted survivor der-A and removed der-C even though they shared one handle.

   Why it matters:
   Disposing der-C can erase the survivor's host entity and then publish a
   logical :ready survivor backed by an invalid/stale handle. This is the
   destructive host/logical divergence BLOCK-001 was intended to prevent.

   Minimum acceptable outcome:
   Re-prove the COMPLETE FINAL action class immediately before action creation:
   every member resolves exactly once to a distinct current SourceSnapshot
   EdgeRecord, distinct derived_id, and distinct valid live handle; survivor
   and removal handle sets are disjoint; issue evidence covers the final source
   member set. Missing, stale, ambiguous, incomplete, repeated, or aliased
   identity fails closed with a truthful audit result.

   Recheck evidence:
   - Three exact members, evidence A-B/B-C, with A/C handle alias => no runnable
     remove action and an explicit fail-closed audit row.
   - Three exact members with distinct handles => one safe deterministic action
     with complete sorted provenance union.
   - Missing/invalid non-survivor handle and survivor/removal alias are direct,
     non-vacuous tests against the final merged class.

2. [V15-STAGE-BLOCK-002] Non-transitive classes and bucket-boundary candidates
   remain unsafe/incomplete.

   Location:
   - extension/su_ai_plugin/core/duplicate_repair_proposer.rb:717-906
   - extension/su_ai_plugin/core/derived_duplicate_validator.rb:90-136
   - extension/su_ai_plugin/core/analyzers/duplicate_detector.rb:42-112
   - tests/test_v15_duplicate_repair.rb:3113-3168

   Problem:
   The closure-failure branch calls union-find again. Union-find produces
   connected components, not cliques, so A~B and B~C still merge A/B/C when
   A!~C. The validator uses the same transitive connected-component rule.
   Separately, DuplicateDetector shifts both endpoint bucket coordinates by one
   shared 3-D vector; it does not enumerate independent start/end boundary
   combinations, so a valid match can be missed when only one endpoint crosses
   a cell boundary.

   The new V15-B002-5 test is not a genuine proof: B is colocated with A and C
   is shifted by 5e-4, so B~C is outside the 1e-4 tolerance. Its assertion also
   examines only affected_derived_ids; it cannot see lexicographic survivor
   der-A, so it does not prove the action has at most two members.

   Why it matters:
   The proposer can delete a member that is outside tolerance from the chosen
   survivor, while the production detector can miss a valid duplicate. The
   proposer/validator/detector therefore do not implement one truthful
   canonical matching contract.

   Minimum acceptable outcome:
   Use a deterministic complete-direct-match class rule (clique partition) or
   fail the entire non-transitive component closed. Candidate enumeration must
   guarantee that every forward/reversed endpoint pair within captured
   tolerance is compared; buckets remain acceleration only. Proposer and
   validator must share both direct predicate and class semantics.

   Recheck evidence:
   - Genuine A=0, B=0.75*tol, C=1.5*tol with issues A-B and B-C proves no
     three-member action (inspect survivor plus removed members).
   - Boundary cases where only start, only end, opposite endpoints, different
     axes, and reversed endpoints cross cells all produce the expected issue.
   - Just-outside cases remain absent; validator reports the same class split
     used by the proposer.

   absence. Any preflight/validation mismatch opens no host operation and

     prevalidated result.
   - Commit failure/uncertainty => :failed, never READY, with explicit recovery.
