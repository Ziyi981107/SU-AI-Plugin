V15-STAGE-BLOCK-001 -- AUTO-APPLY DOES NOT PROVE CANONICAL CLASS MEMBERSHIP
---------------------------------------------------------------------

Original locations:
  extension/su_ai_plugin/core/duplicate_repair_proposer.rb:187-260
  extension/su_ai_plugin/core/duplicate_repair_proposer.rb:212-226
  extension/su_ai_plugin/core/duplicate_repair_proposer.rb:426-474

Problem:
  Auto-apply does not prove that every derived class member resolves
  unambiguously to one distinct current-snapshot source EdgeRecord and one
  distinct live derived Edge record/handle. Container-only first-match lookup
  is not full leaf/occurrence identity. One valid issue pair can authorize
  additional records merely because they share a canonical bucket, without
  proving that duplicate evidence covers the complete contributing source set.

Why this matters:
  An unrelated, stale, repeated, or ambiguously sourced derived record could be
  swept into a destructive removal class. That violates source-occurrence
  identity/provenance and can corrupt canonical class membership.

Minimum acceptable outcome:
  - Before an action is auto-applicable, EVERY derived member resolves to
    exactly one current SourceSnapshot EdgeRecord using full occurrence/leaf
    identity, with the existing deterministic transient-root fallback only
    where the frozen snapshot contract permits it.
  - Source EdgeRecords are distinct; derived records and live handles are
    distinct. Repeated source identity, ambiguous lookup, missing handle,
    self-match, repeated reference, or incomplete nested identity fails closed
    with a truthful skipped audit.
  - Valid duplicate_edge_candidate evidence covers the contributing source
    EdgeRecord set for the complete class. One pair cannot silently authorize
    unrelated additional members.
  - Source occurrences remain immutable and distinct. Only after every guard
    passes may the survivor carry the deterministic sorted provenance union.

Recheck evidence required:
  - two same-transform component instances resolve to distinct source records
    and apply safely;
  - repeated reference to the same source edge is skipped;
  - an unrelated derived record in the same geometry candidate bucket but
    absent from issue evidence is not swept into the action;
  - ambiguous, missing, or non-full-leaf resolution is skipped;
  - incomplete nested provenance is covered by an explicit fail-closed test.

V15-STAGE-BLOCK-002 -- BUCKETING IS NOT THE DIRECT TOLERANCE CONTRACT
---------------------------------------------------------------------

Original locations:
  extension/su_ai_plugin/core/duplicate_repair_proposer.rb:352-370
  extension/su_ai_plugin/core/duplicate_repair_proposer.rb:406-423
  extension/su_ai_plugin/core/derived_duplicate_validator.rb:77-99
  extension/su_ai_plugin/core/derived_duplicate_validator.rb:101-140

Problem:
  round(coordinate / tolerance) is treated as the match rule. Within-tolerance
  endpoints can straddle bucket boundaries, while records admitted only by
  bucket membership are not necessarily a valid direct match. The proposer and
  validator therefore can disagree with the locked duplicate rule, and a
  non-transitive A~B, B~C, A!~C chain can form an unsafe destructive class.

Why this matters:
  Valid duplicates can be missed, invalid members can be deleted, and post-
  validation can make a false correctness claim.

Minimum acceptable outcome:
  - Spatial buckets are candidate acceleration only.
  - The same tested matcher performs forward/reversed direct endpoint
    comparison with the CAPTURED execution-config duplicate tolerance for every
    member admitted to an action and every class counted by validation.
  - Adjacent buckets are handled deterministically.
  - Non-transitive chains never become one destructive class unless every
    required direct relationship of the chosen canonical-class rule is proven;
    otherwise split deterministically or fail closed.
  - Proposer and validator share exactly the same direct matcher semantics.

Recheck evidence required:
  - within-tolerance endpoints across a rounding boundary are recognized;
  - just-outside-tolerance endpoints are skipped;
  - a non-transitive three-edge chain cannot cause unsafe three-member deletion;
  - reversed endpoint ordering across a bucket boundary has the same safe
    result.

V15-STAGE-BLOCK-003 -- LOGICAL POST-STATE CHECK OCCURS AFTER HOST COMMIT
---------------------------------------------------------------------

Original locations:
  extension/su_ai_plugin/core/duplicate_repair_executor.rb:336-369
  extension/su_ai_plugin/core/duplicate_repair_executor.rb:401-457
  extension/su_ai_plugin/core/duplicate_repair_executor.rb:560-606

Problem:
  The SketchUp operation is committed before logical post-workspace
  construction/checking. On later mismatch the code attempts abort after
  commit, which cannot undo a successful committed host mutation. The method
  can return pre-batch logical inventory as :failed even though SketchUp has
  already deleted derived entities.

Why this matters:
  Logical state and SketchUp host state can diverge. Recovery or Discard may
  then operate on stale handles and cannot truthfully establish what happened.

Minimum acceptable outcome:
  - In pure data and BEFORE opening the host operation, preflight and construct
    the complete non-overlapping post-inventory, survivor replacements,
    provenance unions, expected fingerprint/shape, action/handle validity, and
    validation result.
  - Open one operation only after all preflight invariants pass; dispose only
    validated non-survivors; abort on any dispose failure; commit once on
    success; then publish the already-precomputed logical post-workspace.
  - No path attempts abort after a successful commit.
  - Begin/commit/abort ordering and outcome are explicit. Commit/abort
    uncertainty remains visible and recoverable and can never yield READY or a
    fabricated rollback claim.

Recheck evidence required:
  - preflight failure proves begin_operation was never called;
  - Nth dispose failure produces one begin, one abort, zero commit, and exact
    pre-batch logical inventory/provenance;
  - successful batch produces one begin, one commit, zero abort;
  - a forced logical post-state/preflight mismatch cannot commit host deletion;
  - commit failure remains :failed and does not report fabricated rollback.
