ANSWERS TO THE SEVEN PRE-FLIGHT QUESTIONS
======================================================================

1. Clean seam for a derived workspace?

YES, with a required contract extension. The existing boundary is good:
SketchUp access is concentrated in extension/compatibility code, while the
analyzers consume a pure-Ruby GeometrySnapshot. AnalyzersRunner already builds
one snapshot per command. Add V1.4 alongside this seam; do not place host writes
inside analyzers or the current read-only records.

The current GeometrySnapshot is not yet a complete V1.4 SourceSnapshot. It
does not capture snapshot identity/fingerprint, explicit unit/coordinate
context, workspace/profile/rule versions, or sufficient transform context for
all future reconstruction decisions. Its immutability is also shallow: arrays
are frozen at the aggregate level, while nested point arrays, metadata and
preflight values can still be mutable. It may be evolved compatibly or wrapped,
but it must not be treated as a safe rebuild contract unchanged.

2. Source identity/provenance strong enough?

PARTIALLY. Complete persistent_id_path plus structural_depth and
pid_path_complete correctly distinguish nested occurrences, including shared
component definitions. The locator correctly fails closed for incomplete
nested paths instead of using entityID as false occurrence identity.

V1.4 must add a snapshot-local occurrence/record identity that is always unique
within one snapshot, separate from host-resolvable identity. For every source
record, preserve identity quality explicitly (resolvable complete PID path vs
transient root fallback vs unresolved nested occurrence). Never claim stable
cross-session provenance when pid_path_complete is false. A display-only
instance_path/object_id label is not canonical provenance.

3. Snapshot/world-coordinate model safe for later canonical topology?

YES AS A FOUNDATION, NOT AS-IS AS THE FINAL CONTRACT. The traversal correctly
accumulates parent * child transformations, seeds active edit transform, emits
one occurrence per shared component instance, and stores edge endpoints in
world coordinates. This is the right canonical-analysis direction.

Before derived creation, freeze an explicit coordinate policy:
- raw source coordinates and derived/canonical coordinates remain distinct;
- SketchUp internal lengths remain inches;
- world-space snapshot values record how they were obtained;
- workspace insertion coordinates are explicitly converted for the chosen
  destination context (root/active context), never assumed;
- active-edit, nested transform and shared-definition cases are regression
  fixtures.

Do not add normalization or change Z in V1.4.

4. Existing UI/highlight/settings mutation danger?

NO CURRENT ENTITY-MUTATION PATH WAS FOUND. IssueLocator changes Selection and
camera zoom only; the repository scan found no existing erase/transform/entity
attribute write path. This remains view-state, not source-geometry mutation.

V1.4 source-vs-derived presentation must preserve this rule. Do not recolor,
re-layer, hide, transform, or attach persistent diagnostics to source entities.
Selection/camera changes may remain reversible UI behavior. UI must make source,
working mode, invalid workspace, discard and rebuild states understandable.

5. Reproducible config/profile/tolerance architecture?

PARTIALLY. AnalysisConfig and Tolerance provide a centralized entry point and
inch-based values; LayerRoleConfig has explicit ordered rules and rule IDs.
However, there is no complete persisted/versioned execution context. Profile
name alone and live constants are insufficient to reproduce a repair plan.

V1.4 must capture an immutable execution-config snapshot containing at least:
- profile identifier and profile version;
- rule-set identifier/version (or deterministic digest);
- tolerance schema/version and all effective numeric values;
- relevant session overrides;
- SourceSnapshot/schema version.

Repair actions read only this captured context. Do not scatter new thresholds
or layer-name rules through workspace/repair code. Add only the minimum
persistence needed for reproducibility.

6. SU2017+ compatibility invalidates the architecture?

NO. The existing capability-adapter pattern, persistent-ID probing, HtmlDialog
boundary, world-transform traversal and pure-Ruby core are compatible with the
planned architecture. Continue the actual minimum Ruby-runtime syntax baseline
used by this repo and capability detection instead of scattered version checks.

Any new SketchUp calls for groups/entities/model operations must be isolated
behind host adapters and fail safely when unavailable. SU2020 real-host evidence
is required for the V1.4 exit gate. SU2017 remains a separate pending real-host
gate; automated or SU2020 evidence must not be relabeled as SU2017 evidence.

7. Existing architectural choice requiring correction before bulk repair?

NO PRE-V1.4 BLOCK, but two V1.4 internal gates are mandatory before the first
mutation-capable implementation is allowed to proceed:

A. Make the SourceSnapshot/rebuild input deeply immutable or defensively copied,
   versioned, fingerprintable, and explicit about coordinate/identity quality.

B. Prove derived geometry owns independent editable geometry. Never create a
   derived ComponentInstance that still shares a ComponentDefinition with the
   source and then edit that definition. Shared-definition aliasing would mutate
   source CAD indirectly and is a release BLOCK.

These are the expensive seams. Solve and test them first inside V1.4; no broad
V1.0-V1.3 refactor is requested.

PI IMPLEMENTATION DIRECTIVE - V1.4 ONLY
======================================================================

Product invariant:

SOURCE CAD IS IMMUTABLE. ALL PREPARE/REPAIR WRITES TARGET A DISPOSABLE,
PLUGIN-OWNED DERIVED WORKSPACE. UNDO IS ADDITIONAL SAFETY, NOT THE ONLY
RECOVERY MECHANISM.

Recommended meaningful stages (Pi may rename/split helpers without review):

Stage 1 - Freeze the source/rebuild contract

- Introduce or compatibly extend the SourceSnapshot contract.
- Add snapshot/schema identity, selection-scope identity, unit/coordinate
  metadata, transform context, execution-config snapshot, source fingerprint,
  and snapshot-local occurrence IDs.
- Preserve existing V1.0-V1.3 analyzer behavior and payload contracts.
- Define a deterministic fingerprint comparison suitable for proving zero
  source mutation. It must cover material source state, not only edge count.
- Do not use live SketchUp entity objects as the authoritative rebuild input.

Stage 2 - RepairPlan pure-data foundation

- Implement explicit RepairAction/RepairPlan lifecycle and validation without
  applying substantive repairs.
- Minimum semantics: action_id/type, rule_id, evidence-driven confidence,
  explanation, source occurrence IDs, affected derived IDs, before/proposed
  after summary, topology impact, auto_applicable, status and validation result.
- Use proposed/applied/skipped/rejected/failed states; failed plans/results are
  never READY.
- No fake AI confidence and no short-edge deletion policy.

Stage 3 - DerivedGeometryWorkspace ownership and host adapter

- Create a plugin-owned, visually identifiable, disposable workspace from the
  frozen source snapshot.
- Every editable derived entity must be independently owned; no shared mutable
  definition or attribute container may alias source.
- Preserve derived-record -> source-occurrence provenance.
- Choose and document the destination coordinate context, then perform explicit
  world/local conversion at the adapter boundary.
- Wrap host writes in compatible SketchUp operations. On exception, abort or
  invalidate the partial derived result; source remains untouched. If cleanup
  cannot complete, the result must require discard/rebuild and must not appear
  valid or READY.
- Apply/discard/rebuild must operate only on the plugin-owned workspace.
- A second build from identical source + captured config must produce the same
  canonical derived fingerprint, excluding documented host-assigned IDs.

Stage 4 - Minimal working-mode UI and integration

- Enter working/prepared mode, show source vs derived ownership, show config
  identity, and expose discard/rebuild.
- Repair preview plumbing may render no-op/proposed actions, but V1.5 repair
  behavior stays out of scope.
- Do not permanently modify source appearance to distinguish it.
