V15-STAGE-BLOCK-001 -- AUTO-APPLY DOES NOT PROVE DISTINCT SOURCE MEMBERS
---------------------------------------------------------------------

Locations:
  extension/su_ai_plugin/core/duplicate_repair_proposer.rb:187-260
  extension/su_ai_plugin/core/duplicate_repair_proposer.rb:212-226
  extension/su_ai_plugin/core/duplicate_repair_proposer.rb:426-474

Problem:
  Guidance 031 section 5 requires every class member to resolve to a distinct
  source EdgeRecord and a distinct live derived Edge record/handle. The code
  explicitly says it does NOT enforce distinct source records/occurrences.
  One valid issue merely authorizes every derived record in the same canonical
  bucket. The proposer does not prove that each member maps unambiguously to a
  current-snapshot source edge or that all class members are covered by the
  duplicate evidence. edge_for_occurrence_id also uses container-only matching
  and returns the first edge, which is not an unambiguous leaf resolution.

Why this matters:
  Auto-delete may sweep an unrelated/stale/duplicated derived record into a
  removal class. This is exactly the provenance/source-authority risk the guard
  was intended to prevent.

Minimum acceptable fix:
  - Before emitting an auto-applicable class, resolve EVERY derived member to
    exactly one current SourceSnapshot EdgeRecord using full occurrence/leaf
    identity (with the existing deterministic transient-root fallback only
    where the snapshot contract permits it).
  - Require distinct source EdgeRecords and distinct live derived records /
    handles. Repeated source identity, ambiguous lookup, missing handle, or
    incomplete nested identity MUST fail closed with an explicit skipped audit.
  - Require the valid duplicate_edge_candidate evidence for that canonical
    class to cover the contributing source EdgeRecord set; one pair must not
    silently authorize unrelated additional members.
  - Keep both source occurrences immutable; survivor provenance is the sorted
    union only after all guards pass.

Recheck tests required:
  - two same-transform component instances -> distinct source records -> apply;
  - repeated reference to the same source edge -> skipped;
  - extra unrelated derived record in the same geometry bucket but absent from
    issue evidence -> not swept into the action;
  - ambiguous/missing/full-leaf resolution -> skipped;
  - incomplete nested provenance -> skipped (explicit test, not "implicit").

V15-STAGE-BLOCK-002 -- TOLERANCE BUCKET IS NOT THE MATCH CONTRACT
---------------------------------------------------------------------

Locations:
  extension/su_ai_plugin/core/duplicate_repair_proposer.rb:352-370
  extension/su_ai_plugin/core/duplicate_repair_proposer.rb:406-423
  extension/su_ai_plugin/core/derived_duplicate_validator.rb:77-99
  extension/su_ai_plugin/core/derived_duplicate_validator.rb:101-140

Problem:
  round(coordinate / tolerance) is used as if every pair within tolerance lands
  in the same bucket. That is false at cell boundaries. Conversely, only the
  source issue pair is directly reverified; every derived class member and the
  validator are accepted solely by bucket membership.

Why this matters:
  Valid exact-within-tolerance duplicates may be missed, and the derived
  validator may disagree with the actual locked duplicate rule. A chained
  near-match must also not let non-matching endpoints join an unsafe class.

Minimum acceptable fix:
  - Treat spatial buckets only as candidate acceleration.
  - Perform forward/reversed direct endpoint comparison with the CAPTURED
    tolerance for every member admitted to an action and every class counted by
    post-validation.
  - Deterministically handle adjacent buckets. Do not merge a non-transitive
    A~B, B~C, A!~C chain into one destructive class; split deterministically or
    fail closed.
  - Use the same tested matcher in proposer and derived validator so their
    semantics cannot drift.

Recheck tests required:
  - within-tolerance endpoints straddling a rounding boundary -> recognized;
  - just-outside tolerance -> skipped;
  - non-transitive three-edge chain -> no unsafe three-member deletion;
  - reversed ordering across a bucket boundary -> same safe result.

V15-STAGE-BLOCK-003 -- POST-STATE CHECK OCCURS AFTER COMMIT
---------------------------------------------------------------------

Locations:
  extension/su_ai_plugin/core/duplicate_repair_executor.rb:336-369
  extension/su_ai_plugin/core/duplicate_repair_executor.rb:401-457
  extension/su_ai_plugin/core/duplicate_repair_executor.rb:560-606

Problem:
  The executor commits the SketchUp operation at line 404, constructs and
  checks the logical post-workspace afterwards, and on mismatch tries to abort
  at line 445. An abort after successful commit cannot undo the committed host
  mutation. The method can therefore return the pre-batch logical inventory in
  :failed while SketchUp has already deleted derived entities.

Why this matters:
  Host state and the plugin's source-of-truth inventory can diverge. Recovery /
  Discard may then operate on stale handles, which is a material corruption and
  recoverability risk.

Minimum acceptable fix:
  - Implement Guidance 031 section 7 literally: preflight and construct the
    COMPLETE non-overlapping post-inventory, survivor replacement records,
    expected fingerprint/shape, action/handle validity, and validation result
    in pure data BEFORE opening the operation.
  - Begin once, dispose only validated non-survivors, abort on any dispose
    failure, commit once on success, then publish the already-precomputed
    post-workspace.
  - No code path may attempt abort after a successful commit.
  - Commit/abort uncertainty must remain visible and recoverable; never claim
    READY from an uncertain host transaction.

Recheck tests required:
  - preflight failure proves begin_operation was never called;
  - Nth dispose failure -> one begin + one abort + zero commit and exact
    pre-batch logical inventory/provenance;
  - successful batch -> one begin + one commit + zero abort;
  - forced logical post-state/preflight mismatch cannot commit host deletion;
  - commit failure remains :failed and does not report a fabricated rollback.

    applied/skipped/failed, classes before/after, derived edge count before/
    after, real pair/member-removal counts.
  - Preserve source issue IDs/keys in each action audit.
  - Expose per-action status, rule/explanation, removed count, survivor ID, and
    source-occurrence count in a read-only details block (or equally inspectable
    structure). Continue to use textContent; no innerHTML/eval.

Recheck tests required:
  - validator on an unchanged duplicate workspace reports remaining > 0;
  - validator on repaired post-workspace reports 0;
  - non-default captured tolerance is used end-to-end;
  - summary before/pairs/edge counts are non-fabricated and exact;
