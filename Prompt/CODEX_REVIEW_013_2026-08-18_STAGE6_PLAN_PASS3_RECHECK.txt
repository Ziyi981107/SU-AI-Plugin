1. [S6-PLAN-BLOCK-001] `pid_path_complete` must cover the entire path, including leaf PID

   Location:
   - STAGE_6_PLAN_REVISED_2026_08_18_PASS3.md §3.2 lines 163-166
   - §3.10 lines 327-343
   - §6.3 complete-root/incomplete-root profiles
   - BLOCK_RECHECK_REQUEST pass3, BLOCK-001 items A/E

   Problem:
   Pass 3 defines `pid_path_complete` as true iff every CONTAINER PID was captured.
   That is insufficient. A root-level Edge has no container, so this definition makes
   `pid_path_complete == true` even when the leaf Edge PID is nil and its path is `[]`.
   The locator will classify it as complete-root, attempt empty-path resolution, and
   never reach the required root entityID fallback.

   The same defect exists for nested sources: all container PIDs may exist while the leaf
   PID is missing. The path is still incomplete and must not be sent to
   instance_path_from_pid_path. The pseudocode variable `yield_pid_complete` is not
   defined precisely enough to repair the written contract.

   Why it matters:
   This breaks mandatory test case 3 (root missing leaf PID + entityID fallback) and can
   mislabel incomplete nested paths as safe. This is the last material locator-contract
   gap before implementation.

   Minimum acceptable fix:
   A. Define `pid_path_complete` as:
        every structural ancestor PID AND the leaf Entity PID were captured.

   B. Compute it at the leaf yield/build_source_reference point, not only while visiting
      containers. A clear invariant is:
        expected_pid_count = structural_depth + 1
        pid_path_complete = ancestry_complete && !leaf_pid.nil? &&
                            pid_path.length == expected_pid_count
      If active edit context contributes to structural_depth, its PIDs must be included
      in the same expected count.

   C. Fail closed when the invariants disagree. A non-empty but incomplete path must never
      be treated as complete-root or complete-nested.

   D. Make SourceReference wording, SourceToken wording, locatable derivation and the
      five mandatory tests use this full-path definition consistently.

   E. Add/retain explicit cases for:
        - root leaf PID missing, path [], entityID present -> entityID fallback
        - nested container PIDs present but leaf PID missing -> non-locatable
      The second case is distinct from “container PID missing, leaf PID present”.

   Recheck evidence needed:
   - revised §3.2/§3.10/§6.3 and packet wording only
   - test matrix includes both missing-leaf and missing-container shapes
