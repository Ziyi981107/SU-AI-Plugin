0. PURPOSE
======================================================================

This contract resets and freezes the reviewer role, review cadence, reasoning
effort, authority boundaries, artifact naming, and recheck behavior for the
remaining SU-AI-Plugin V1.x work.

Goals:
- spend Codex/GPT-5.6 Sol only where direct source/Git/diff review has high leverage;
- preserve Pi autonomy for routine implementation;
- preserve AIPM/Owner authority over product scope and UX;
- prevent Reviewer self-expansion into workflow dispatcher or Product Owner;
- use xHigh only for genuinely high-risk technical seams;
- prevent repeated whole-repo review and unnecessary review gates;
- keep already-passed unchanged scope closed.

This contract supplements PROJECT_HANDOFF, CURRENT_STATE, the V1.x Product &
Technical Master Plan, Review Agent Playbook, and Coding Agent Playbook.

If an old Prompt/Review instruction conflicts with this file on REVIEW PROCESS
or ROLE AUTHORITY, this contract wins. It does not silently change frozen
product behavior.

Risk-triggered review is appropriate when:
- source CAD may be modified;
- source/derived ownership becomes uncertain;
- undo/discard/rebuild/rollback semantics are uncertain;
- logical state and SketchUp host state may diverge;
- identity/provenance is ambiguous or corruptible;
- coordinate transforms/units/tolerance semantics may be wrong;
- destructive topology merge/delete/snap can affect correctness;
- compatibility/release contract breaks;
- installed RBZ/real-host startup fails;
- Pi cannot confidently resolve a material high-risk technical issue.

Do NOT review:
- every commit;
- every Pi milestone;
- every minor version;
- NIT-only changes;
- unchanged passed modules.

6. GPT-5.6 SOL REASONING EFFORT CONTRACT
======================================================================

DEFAULT CODEX REVIEW:
  HIGH

Use HIGH for:
- ordinary stage review;
- coherent implementation diff review;
- narrow BLOCK recheck where architecture did not materially change;
- packaging/regression review;
- local fix verification;
- normal V1.x code correctness review.

Use xHigh when one or more of these are material:

A. SOURCE / STATE INTEGRITY
- source geometry/data can be mutated;
- derived/source ownership;
- logical vs host-state divergence;
- state corruption;
- stale authoritative inventory.

B. TRANSACTION / RECOVERY
- begin/commit/abort;
- Undo/rollback;
- atomicity;
- partial failure;
- crash/interruption recovery;
- compensation;
- discard/rebuild correctness.

C. IDENTITY / PROVENANCE
- source occurrence identity;
- component-instance identity;
- persistent/transient fallback identity;
- source -> derived provenance;
- stale handles;
- provenance union/survivor semantics.

D. GEOMETRY-CORRECTNESS FOUNDATION
- world/local transforms;
- units;
- tolerance semantics;
- canonical topology;
- destructive merge/delete/snap;
- graph connectivity whose error propagates downstream.

E. MAJOR COMPATIBILITY / RELEASE
- target-host compatibility architecture materially changes;
- package/load/runtime release contract materially changes;
- final release review.

F. EXPENSIVE-TO-REVERSE ARCHITECTURE
- a wrong choice would force several later V1.x stages to be redesigned;
- data/state ownership changes;
- V2 handoff contract changes.

Do NOT use xHigh merely because:
- a diff is large;
- many tests exist;
- the version number is important;
- Reviewer can imagine more improvements;
- a NIT is subtle;
- the task is called "Stage Review".

xHigh is RISK-BASED.

MAX:
- not a default project setting;
- use only for an exceptional unresolved corruption/root-cause problem after
  xHigh is demonstrably insufficient;
- requires explicit AIPM/Owner decision.

8. BLOCK CLASSIFICATION — HARD STANDARD
======================================================================

A BLOCK must be one of:
- frozen contract violation;
- critical product behavior incorrect;
- source/data corruption risk;
- material state/transaction/recovery risk;
- material security/privacy risk;
- release-critical runtime/compatibility failure;
- missing mandatory safety/recovery behavior;
- false evidence / system claims PASS or READY without measuring it;
- evidence implementation is unsafe to continue/release.

NIT:
- non-blocking quality issue;
- small maintainability improvement;
- minor robustness improvement;
- low-severity edge case.

DEBT:
- larger cleanup/refactor;
- future optimization/extensibility;
- architecture improvement not required for the current contract.

QUESTION:
- product behavior ambiguous;
- UX solution not frozen;
- scope/business/user tradeoff requires AIPM/Owner.

Do NOT disguise reviewer preference, cleaner-code preference, speculative future
extensibility, or one preferred UI implementation as a BLOCK.

======================================================================
9. MINIMUM ACCEPTABLE FIX — OUTCOME, NOT MICRO-DESIGN
======================================================================

For a BLOCK, Codex should define:
- what is unsafe/wrong;
- why it matters;
- the minimum observable technical outcome that must hold;
- direct recheck evidence needed.

Codex should NOT prescribe detailed implementation design unless:
- only one safe approach is compatible with the frozen contract;
- the implementation mechanism itself is the high-risk boundary;
- the current implementation proves the design seam must change.

Pi owns ordinary implementation details.

======================================================================
10. PRODUCT / UX BOUNDARY DURING TECHNICAL REVIEW
======================================================================

Codex MAY BLOCK outcomes such as:
- audit data is fabricated;
- material repair is not inspectable;
- user cannot distinguish success from failure;
- UI claims READY without evidence;
- required user control is missing.

Codex MUST NOT independently freeze the exact UX solution unless it already
exists in the Product Contract.

If technical review discovers:
  "The result must be auditable"

Codex may require:
  "Expose sufficient truthful audit evidence."

But if the exact fields/layout are not frozen, Codex should:
- provide a recommendation;
- classify product/UI ambiguity as QUESTION;
- route the exact visible UX choice to AIPM / Owner.

11. BLOCK RECHECK STANDARD
======================================================================

Normal loop:

Codex reports one coherent BLOCK set
→ Pi implements one complete fix packet
→ Pi runs targeted + relevant regression tests
→ Pi writes one recheck packet
→ Codex rechecks:
   - original BLOCK;
   - directly related diff;
   - direct regressions;
   - only adjacent seams whose risk materially changed.

Do NOT:
- start a fresh whole-repo review;
- search for unrelated new NITs merely because the repo is open;
- reopen passed unchanged scope;
- create one review request per tiny BLOCK edit.

A recheck may discover a NEW BLOCK only if:
- the fix itself creates a new material risk;
- new evidence proves an adjacent contract is broken;
- the prior BLOCK cannot actually be closed without it.

If so, explain the causal relationship.
