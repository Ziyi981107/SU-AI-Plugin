STEP V14-8: Failure injection -- abort SU operation + zero partial groups
======================================================================

This step requires you to inject a host failure during
Prepare. The V1.4 plumbing path supports this via the
Ruby console (the production adapter's `begin_operation`
is the failure surface).

Per BLOCK-R3-3: the snippet uses a ONE-SOT SELF-RESTORING
patch. The FIRST `begin_operation` call (the one triggered
by the click) restores the original method BEFORE raising
the injected failure. This guarantees:

  - The patch is INSTALLED BEFORE the Owner click (a
    probe call would raise; the `instance_method` is
    NOT the original).
  - The click triggers the injected failure exactly
    ONCE (one-shot).
  - AFTER the click, the patch is GONE (V14-9 and V14-10
    run against the original production adapter; no
    pollution).
  - NO `begin / ensure` block is required (the previous
    `ensure` pattern restored IMMEDIATELY, before the
    Owner click could happen -- BLOCK-R3-3 forbids that).

======================================================================
PASTE-RUNNABLE RUBY CONSOLE SNIPPET (V14-8, ONE-SOT, LABEL-TARGETED)
======================================================================

  # V14-8: inject a host failure into the production
  # adapter's begin_operation ONLY when the operation
  # label corresponds to the Prepare path. Discard /
  # Discard-cleanup operations also call begin_operation,
  # and a generic one-shot patch would be CONSUMED by
  # the prior Discard (the user clicks Discard first to
  # clear the previous workspace), so the Prepare click
  # would NOT actually receive the injection. The
  # label-targeted patch (Working Copy Prepare) below
  # matches only the workspace Prepare begin_operation,
  # so the prior Discard's begin_operation runs the
  # ORIGINAL method and the Prepare click triggers the
  # one-shot injection.
  #
  # Ruby 2.2.4 / SketchUp 2017+ syntax: no &., no case/in,
  # no pattern matching, no numbered params. String match
  # on the operation label.
  #
  # ABSOLUTE PATHS -- replace `D:/Projects/SU-AI-Plugin`
  # with the actual project root on your machine.
  require 'D:/Projects/SU-AI-Plugin/extension/su_ai_plugin/compatibility/su_derived_workspace_adapter'

  ADAPTER  = SUAnalysis::Compatibility::SketchupDerivedWorkspaceAdapter
  ORIGINAL = ADAPTER.instance_method(:begin_operation)
  TARGET_LABEL = 'SU-AI-Plugin: V1.4 Working Copy Prepare'

  # Install the LABEL-TARGETED one-shot self-restoring
  # patch. The patched method:
  #   - If label.to_s.include?(TARGET_LABEL):
  #       RESTORE the original method FIRST, then raise
  #       the injected failure. Subsequent calls (V14-9,
  #       V14-10, and any later Discard) run ORIGINAL.
  #   - Else (Discard / Discard-cleanup / other labels):
  #       call ORIGINAL.bind(self).call(model, label: label)
  #       verbatim. No side effect.
  ADAPTER.class_eval do
    define_method(:begin_operation) do |model, label:|
      if label.to_s.include?(TARGET_LABEL)
        # RESTORE FIRST so subsequent calls run the original.
        ADAPTER.class_eval do
          define_method(:begin_operation, ORIGINAL)
        end
        # THEN raise the injected failure (one-shot).
        raise StandardError, 'v14-gate-2-injected-failure'
      else
        # Not the Prepare label -- call the original method
        # directly (this is the Discard / Discard-cleanup
        # path; it MUST work normally).
        ORIGINAL.bind(self).call(model, label: label)
      end
    end
  end

  # At this point, the patch IS installed for Prepare but
  # NOT for other operation labels. Verify by reading the
  # instance_method (it is now the patched closure, NOT
  # the original):
  #   ADAPTER.instance_method(:begin_operation) != ORIGINAL
  #     # => true (patch installed)
  #
  # Click "Discard" first (to clear any current workspace;
  # the Discard begin_operation label is
  # "SU-AI-Plugin: V1.4 Derived Workspace -- Discard <id>",
  # which does NOT include TARGET_LABEL, so Discard runs
  # the original begin_operation), then click "Prepare".
  # The Prepare click triggers the one-shot injection.

  # Verification step (paste AFTER clicking Prepare):
  ADAPTER.instance_method(:begin_operation) == ORIGINAL
  # => true (patch has been restored by the one-shot)

STEP V14-10 -- SHARED DEFINITION WORDING NOTE
======================================================================

Per the V1.4 directive (gate A: snapshot-local occurrence
identity distinct from host-resolvable identity) and the
master plan §17.2 (two instances sharing one definition
are not the same world-space geometry), the correct
formulation is:

  - Two ComponentInstance entities in the model SHARE one
    ComponentDefinition. The shared ComponentDefinition is
    the same source-side artifact. Each ComponentInstance
    is a DIFFERENT OCCURRENCE of that definition in the
    model: it has its OWN transform, its OWN host
    persistent_id (each instance gets a unique persistent_id
    when placed), and its OWN persistent_id_path.
  - The Edges inside the shared ComponentDefinition are
    the SAME in BOTH instances -- they live in the
    definition's entities, not in the instance's entities.
    BUT because each instance carries a different
    transform / persistent_id_path, the WORLD-SPACE
    occurrences of those edges in the two instances are
    DIFFERENT occurrences.
  - The V1.4 SourceSnapshot records the source edges AS
    world-space OCCURRENCES (one per instance-edge pair),
    each with its OWN source_occurrence_id derived from
    the FULL persistent_id_path. Two same-definition
    instances produce DIFFERENT snapshot-local occurrence
    IDs for what is logically the same definition edge.
  - The 8 derived edge groups in this scenario are 8
    INDEPENDENT derived occurrences: 2 instances x 4
    edges per definition = 8 world-space edge occurrences.
    They are not collapsed to 4 by shared definition.

Do NOT phrase this as "two instances with the SAME
persistent_id" -- each ComponentInstance in the model
gets its OWN persistent_id when placed. The thing they
share is the ComponentDefinition (the source definition).

OWNER FLOW -- NEW SELECTION MUST RE-ANALYZE
======================================================================

The Working Mode surface operates on the SourceSnapshot
captured at the time the user clicked "Analyze selection".
When the selection CHANGES (new selection, different
geometry, different test fixture), the Owner MUST click
"Plugins > Analyze selection" AGAIN on the new selection
to refresh the AnalysisResult and the SourceSnapshot
before clicking Prepare.

Reusing the previous AnalysisResult / SourceSnapshot
for a different selection is an OWNER TEST-FLOW ERROR,
not a product coordinate defect. The Owner observed this
in V14-10 nested-groups case: the world-coordinate check
returned false until the Owner clicked Analyze selection
again on the new nested selection, after which it
returned true.

  - Test scripts must NOT reuse an AnalysisResult across
    selections.
  - Each new selection must produce a fresh AnalysisResult
    (via the controller's selection -> Analyze selection
    path) and a fresh SourceSnapshot.
  - If a test helper is reused across two different
    selections, the helper must construct a NEW
    AnalysisResult for the second selection (and a NEW
    SourceSnapshot derived from it). Re-using a stale
    AnalysisResult will produce stale-derived coordinates
    and is documented as a test-flow bug, not a product
    bug.
